### 5.3 Store-Scoped Roles

Roles `store_keeper` and `site_engineer` can ONLY see data for their assigned store.
Implementation: Global Scope on models that have `store_id`.

```php
// App\Traits\ScopesByStore
trait ScopesByStore
{
    protected static function booted()
    {
        if (in_array(auth()->user()?->roles->first()->name ?? '', config('erp.store_scoped_roles'))) {
            static::addGlobalScope('store', function ($query) {
                $query->where('store_id', auth()->user()->store_id);
            });
        }
    }
}
```

Apply this trait to: `Inventory`, `InventoryMovement`, `MaterialRequest`, `Transfer`, `MaterialUsage`, `Waste`.

### 5.6 Authorization Middleware

```php
// Or in controllers:

```

### 5.7 Policies

Create one Policy per major model. Example:

```php
// App\Policies\MaterialRequestPolicy
class MaterialRequestPolicy
{
    public function view(User $user, MaterialRequest $mr): bool
    {
        if ($user->hasRole(['global_admin', 'admin'])) return true;
        if ($user->hasRole(['store_keeper', 'site_engineer'])) {
            return $mr->store_id === $user->store_id;
        }
        if ($user->id === $mr->requested_by) return true;
        return $user->can('material_requests.view');
    }

    public function approve(User $user): bool
    {
        return $user->can('material_requests.approve');
    }

    public function issue(User $user): bool
    {
        return $user->can('material_requests.issue');
    }
}
```

Create policies for: Store, Inventory, PurchaseRequest, MaterialRequest, Transfer, SubconAgreement, Payment, Expense, Payroll, Schedule, BoqItem.

## SECTION 7: MODEL RELATIONSHIPS MAP

```
User
  belongsTo(Store)          via store_id
  belongsToMany(Role)       via spatie
  hasMany(ActivityLog)      via spatie
  hasMany(MaterialRequest)  via requested_by
  hasMany(PurchaseRequest)  via requested_by
  hasMany(Transfer)         via requested_by
  hasMany(Issue)            via reported_by
  hasMany(DailyReport)      via created_by
  hasMany(WeeklyReport)     via created_by
  hasMany(WeeklyPlanDispatch) via dispatched_to
  hasMany(ErpPlanTask)      via assigned_to
  hasMany(ErpPlanHeader)    via created_by
  hasMany(Employee)         via user_id (reverse)

Store
  hasMany(Inventory)
  hasMany(InventoryMovement)
  hasMany(MaterialRequest)
  hasMany(Transfer)         via from_store_id
  hasMany(Transfer)         via to_store_id
```

## SECTION 8: CROSS-MODULE BUSINESS FLOWS

### 8.1 Full Procurement Cycle

```
TRIGGER: Material shortage detected (manual or from material_planning)
  ↓
STEP 1: Purchase Request created
  Model: PurchaseRequest (status: draft → submitted)
  Event: PurchaseRequestCreated
  Listener: NotifyUsersWithPermission('purchases.requests.create')
  ↓
STEP 2: Purchase Manager reviews, may merge similar PRs
  Action: PurchaseRequestController@merge
  Effect: Set merged_into_pr_id on duplicate PRs, status → cancelled
  ↓
STEP 3: Market Research — purchaser gets quotes from ≥3 suppliers
  Model: MarketResearch + MarketResearchItems (per supplier)
  Status: pending → submitted
  ↓
STEP 4: Proforma Invoices entered per supplier quote
  Model: ProformaInvoice
  ↓
STEP 5: GM Decision — GM selects winning supplier
  Action: Set gm_selected = true on chosen proforma
  PR status → pending_gm_decision → po_created
  ↓
STEP 6: Purchase Order created from winning proforma
  Model: PurchaseOrder + PurchaseOrderItems (copied from PR items + proforma prices)
  PO status: draft → sent
  Event: PurchaseOrderCreated
  ↓
STEP 7: Delivery Received
  Model: DeliveryReceipt + DeliveryReceiptItems
  Action: Update PO items received_quantity
  PO status → partial_delivery or delivered
  Event: DeliveryReceived
  Listener: CreateInventoryMovementOnDelivery → increments inventory
  ↓
STEP 8: Finance processes payment
  Model: Expense (with reference to PO)
  Event: PaymentRecorded
  Listener: CreateJournalEntryOnPayment
```

### 8.2 Material Request → Issue Flow

```
STEP 1: Site Engineer creates Material Request
  Model: MaterialRequest (status: draft → submitted)
  ↓
STEP 2: Store Manager approves (or rejects with reason)
  Model: MaterialRequest.status → approved
  Model: MaterialRequestItem.approved_quantity set
  ↓
STEP 3: Store Keeper issues materials
  Model: MaterialRequestItem.issued_quantity incremented
  Model: MaterialRequest.status → partially_issued → issued
  Event: MaterialIssued
  Listener: CreateInventoryMovementOnIssue
    → InventoryMovement (type: material_issue, negative)
    → Inventory.quantity_on_hand decremented
    → Inventory.quantity_reserved decremented
```

### 8.3 Transfer Flow

```
STEP 1: Requesting store creates Transfer
  Model: Transfer (status: draft → pending_approval)
  ↓
STEP 2: Source store manager approves
  Model: Transfer.status → approved
  ↓
STEP 3: Source store ships (optional: sent_quantity recorded)
  Model: Transfer.status → in_transit
  Event: TransferShipped
  Listener: CreateInventoryMovement (type: transfer_out, negative at source)
  ↓
STEP 4: Destination store receives
  Model: TransferItem.received_quantity set
  Model: Transfer.status → completed
  Event: TransferCompleted
  Listener: CreateInventoryMovement (type: transfer_in, positive at destination)
```

### 8.4 Subcontractor IPC Payment Flow

```
STEP 1: Subcon Agreement created with BOQ scope items
  Model: SubconAgreement + SubconAgreementItems
  ↓
STEP 2: Work executed on site (progress tracked elsewhere)
  ↓
STEP 3: Contract Admin creates IPC
  Model: IpcRecord + IpcItems
  For each agreement item, enter current_percent complete
  System calculates:
    current_value = boq_value × (current_percent - previous_percent) / 100
  ↓
STEP 4: IPC totals calculated
  current_work_value = sum of all ipc_items.current_value
  current_retention = current_work_value × agreement.retention_percent / 100
  current_certified = current_work_value - current_retention
  cumulative_certified = previous_certified + current_certified
  balance_to_certify = agreement.contract_value - cumulative_certified - agreement.retention_amount
  ↓
STEP 5: Finance approves IPC
  IpcRecord.status → approved
  ↓
STEP 6: Payment recorded
  Model: Expense or Payment with reference to IPC
  SubconAgreement.paid_to_date incremented
  Event: PaymentRecorded → Journal Entry auto-generated
```

### 8.5 Weekly Schedule Dispatch Flow

```
STEP 1: Planning team creates/updates tasks in ErpPlanHeader
  ↓
STEP 2: Resources assigned to tasks via ErpPlanTaskResource
  ↓
STEP 3: Planning Manager dispatches weekly plan
  Model: WeeklyPlanDispatch (status: draft → dispatched)
  Model: WeeklyPlanDispatchTasks (which tasks for this week)
  Event: ScheduleDispatched
  Listener: NotifySiteEngineer
  ↓
STEP 4: Site Engineer sees dispatched tasks in dashboard
  ↓
STEP 5: Foreman creates daily reports referencing dispatched tasks
  ↓
STEP 6: Progress updated on tasks
  Model: ErpPlanTask.actual_progress updated
  Model: ErpPlanHeader.overall_progress recalculated (avg of top-level tasks weighted by cost)
```

### 8.6 Employee Payroll Flow

```
STEP 1: HR adds employee with basic_salary
  ↓
STEP 2: Attendance recorded (manual or ZKTeco biometric sync)
  Model: Attendance records
  ↓
STEP 3: Payroll period ends (e.g., 25th of month)
  ↓
STEP 4: HR calculates payroll
  Service: PayrollService@calculate
  For each active employee:
    basic_salary from employee record
    days_worked from attendance (present + half_day × 0.5)
    overtime_hours from attendance (hours_worked - standard_hours)
    overtime_amount = overtime_hours × (basic_salary / 30 / 8) × overtime_rate_multiplier
    allowances from PayrollItem (type: allowance)
    tax_deduction = calculated per tax bracket
    pension_deduction = basic_salary × pension_rate
    other_deductions from PayrollItem (type: deduction)
    net_salary = gross_salary - total_deductions
  Model: PayrollRecord + PayrollItems created
  ↓
STEP 5: HR Manager reviews → Finance Head approves
  PayrollRecord.status → approved
  ↓
STEP 6: Finance processes payment
  Event: PayrollProcessed
  Listener: CreateJournalEntryOnPayroll
    Debit: Salary Expense (CoA)
    Credit: Bank/Cash (CoA)
    Credit: Tax Payable (CoA)
    Credit: Pension Payable (CoA)
```

### 8.7 Double-Entry Journal Engine Rules

```
TRIGGER → REFERENCE_TYPE → DEBIT ACCOUNT → CREDIT ACCOUNT

Material Issue from Store:
  reference_type: material_issue
  Debit: Project Material Cost (expense CoA)
  Credit: Inventory/Stores (asset CoA)
  Amount: sum of issued items × unit_cost

Purchase Delivery:
  reference_type: purchase_receipt
  Debit: Inventory/Stores (asset CoA)
  Credit: Accounts Payable / GRNI (liability CoA)

Supplier Payment:
  reference_type: supplier_payment
  Debit: Accounts Payable (liability CoA)
  Credit: Bank Account (asset CoA)

Expense Payment (cash):
  reference_type: expense
  Debit: Expense Category CoA
  Credit: Cash/Bank CoA

Income Received:
  reference_type: income
  Debit: Bank Account (asset CoA)
  Credit: Revenue/Income CoA

Payroll:
  reference_type: payroll
  Debit: Salary Expense CoA
  Credit: Bank CoA (net_salary)
  Credit: Tax Payable CoA (tax_deduction)
  Credit: Pension Payable CoA (pension_deduction)

IPC Payment:
  reference_type: ipc_payment
  Debit: Subcontractor Cost CoA
  Credit: Bank CoA
  Credit: Retention Payable CoA (retention portion)

Transfer between stores:
  reference_type: transfer
  Debit: Inventory - Destination Store (asset CoA)
  Credit: Inventory - Source Store (asset CoA)

Waste:
  reference_type: waste
  Debit: Waste/Loss Expense CoA
  Credit: Inventory/Stores (asset CoA)

Journal Engine Implementation:
  Class: App\Services\Finance\JournalEngine
  Method: createEntry(string $referenceType, int $referenceId, string $description, array $lines[])
  Each line: ['account_id' => int, 'side' => 'debit'|'credit', 'amount' => float]
  Validation: total debits MUST equal total credits (within 0.01 tolerance)
  On success: create JournalEntry + JournalEntryLines, update ChartOfAccount.current_balance
```

Every service class goes in `app/Services/{Module}/`. Each encapsulates business logic.

### 11.1 InventoryService

```php
namespace App\Services\Inventory;

class InventoryService
{
    public function getStock(int $storeId, ?int $productId = null): Collection;
    public function getLowStockItems(int $storeId): Collection;
    public function getStockValue(int $storeId): float;
    public function adjustStock(int $inventoryId, float $quantity, string $type, string $reason, int $userId): InventoryMovement;
    public function getStockForProduct(int $productId): Collection; // across all stores
}
```

### 11.2 MovementService

```php
namespace App\Services\Inventory;

class MovementService
{
    public function recordMovement(
        int $inventoryId,
        string $type,           // enum value
        float $quantity,
        ?float $unitCost,
        string $referenceType,
        int $referenceId,
        ?string $notes,
        int $userId
    ): InventoryMovement;
    // This method: reads current balance, creates movement, updates inventory qty_on_hand
    // MUST be called within a DB transaction
}
```

### 11.3 JournalEngine

```php
namespace App\Services\Finance;

class JournalEngine
{
    public function createEntry(
        string $referenceType,
        int $referenceId,
        string $description,
        array $lines,  // [['account_id' => int, 'side' => 'debit'|'credit', 'amount' => float], ...]
        int $createdBy,
        ?int $approvedBy = null
    ): JournalEntry;
    // Validates: total debits == total credits (within 0.01)
    // Creates JournalEntry + JournalEntryLines
    // Updates ChartOfAccount.current_balance (debit adds to asset/expense, credit adds to liability/equity/revenue)
    // If approvedBy provided, auto-posts

    public function postEntry(int $journalEntryId, int $approvedBy): JournalEntry;
    public function cancelEntry(int $journalEntryId, string $reason): JournalEntry;
}
```

```php
namespace App\Services\Schedule;

class ScheduleService
```

SECTION 16: AJAX & DATATABLES SPECIFICATION
All index lists use jQuery DataTables in server-side processing mode.

Standard Controller Datatables Method:

php

public function datatables()
{
    $query = Model::with(['relation1', 'relation2']);
    
    // Apply store scope automatically if trait is used
    
    return DataTables::of($query)
        ->addColumn('actions', function ($row) {
            $html = '';
            if (auth()->user()->can('module.view')) {
                $html .= '<a href="'.route('module.show', $row->id).'" class="btn btn-sm btn-outline-primary"><i class="fas fa-eye"></i></a> ';
            }
            if (auth()->user()->can('module.edit')) {
                $html .= '<a href="'.route('module.edit', $row->id).'" class="btn btn-sm btn-outline-secondary"><i class="fas fa-edit"></i></a> ';
            }
            if (auth()->user()->can('module.delete')) {
                $html .= '<button type="button" class="btn btn-sm btn-outline-danger btn-delete" data-id="'.$row->id.'" data-route="'.route('module.destroy', $row->id).'"><i class="fas fa-trash"></i></button>';
            }
            return $html;
        })
        ->rawColumns(['actions', 'status'])
        ->make(true);
}
